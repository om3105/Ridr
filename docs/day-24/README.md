# Day 24 — restricted sponsored cards

Ridr now has one sponsored-card placement rule. A native card can appear only on Home, Ride History or a loaded completed summary. Starting or restoring an active ride, an ad-free entitlement, an unknown account state, or leaving the screen removes it. The API independently checks current account, ride and entitlement state on every read; a summary request also requires participation in that completed ride. A late response cannot restore a card after the screen or account changes. The app rechecks a visible card every 10 seconds and when it returns to the foreground.

No sponsor is configured by default, so the usual result is no card and no empty placeholder. An operator can provide one approved, non-personalized card with the four `SPONSORED_CARD_*` settings shown in `.env.example`; its action opens the configured HTTPS destination only after a tap. The native card has an explicit “Sponsored” label, a separate high-contrast treatment with a two-pixel border for normal and high-visibility use, and an accessible action. No location, route, member, contact or SOS data is sent to the destination by this feature. No ad SDK, third-party ad request, contextual targeting, reward, purchase or interstitial is enabled in Day 24.

Run `NODE_ENV=test npm run test:sponsored --workspace @ridr/api` with the local database for the current-account, active-ride, ad-free and completed-summary checks. Run the API and mobile suites, type checks, lint and build for the full workspace. Before activating a real sponsor, approve its creative and destination, verify the card on Android and iOS in normal/high-visibility conditions and with screen readers, and test a delayed response while starting a ride or returning to Home. The normal no-fill experience requires no device or advertiser setup.
