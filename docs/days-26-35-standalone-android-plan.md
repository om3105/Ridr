# Revised Days 26–35: independent Android APK and offline recovery

This plan supersedes **Days 26–35** in the original 35-day PDF. Days 1–25 and the Day 1 scope and release gates remain unchanged. The added Day 30 deliverable is an **internally distributed, signed Android APK** that installs and launches without Expo Go, Metro, USB, or a laptop. It is a testable beta candidate, not public-release approval; Days 31–35 still cover field evidence, fixes, and the go/no-go decision.

## Why the schedule needs to change

- The current EAS profile builds a **development client**. The installed phone uses Metro and an API address on the Mac's network. An Expo export or a debug APK does not prove a standalone install.
- Supabase Auth is the only hosted component prepared so far. The Ridr API, private domain database, routing services, private media, status viewer, and push delivery still need reachable, durable deployment and end-to-end verification. Supabase Auth alone cannot replace them.
- Location and message drafts have encrypted queues, but a cold start while disconnected still requires online profile verification before ride tools open. The [Day 15 handoff](day-15/README.md) explicitly leaves the ten-minute, app-restart device gate open.
- MapTiler road tiles and routing need network access. The agreed [Day 1 mapping scope](day-01/backlog.md#sup-14--mapping-and-routing-services) excludes downloadable offline map packs. The app must say when the map is unavailable; it must never show a sample map as a real offline route.
- The [Day 25 checkpoint](day-25/README.md) leaves device, deployment, safety-delivery, and performance evidence open. The old plan's Day 30 wording must not be read as a release pass.

## Day 30 acceptance contract

The APK must be a signed **internal/release-style build with JavaScript and native code bundled**, a stable Android application ID and version code, no development launcher, no Metro dependency, and no cleartext/LAN/localhost endpoint. A fresh install and update from the prior candidate must work on at least one physical Android phone. With the Mac off and USB disconnected, a phone on ordinary mobile data must be able to sign in with a verified test account, load a ride, exchange data with another member, render an online road map, and reach the deployed API. Save the APK, SHA-256 checksum, build configuration, install instructions, and device evidence.

**Offline means a bounded continuation of a previously opened, authorized ride:** clear offline/stale status; access to an encrypted, account-scoped last-known ride summary and route information; continued eligible location capture only while explicit consent and OS permission remain valid; durable encrypted location, text, and preset queues across app restart; visible pending capacity; local stop-sharing and end/leave intent that does not claim server acceptance; and safe reconciliation before replay. Manual SOS while disconnected must say **“Not sent — offline”** and must not imply emergency services were contacted. On reconnection, fetch authoritative ride/session state before replay, deduplicate IDs, respect consent epochs and remote end, and meet the Day 1 bounded recovery test: ten-minute outage with app restart, fresh live position within ten seconds, and queued history/text within sixty seconds after stable reconnect.

New sign-in, create/join, route calculation or save, media upload, live peer positions, push delivery, external status-link reads, and third-party road tiles require connectivity. Downloadable road maps are **not included in the current baseline**; this scope assumption must be revisited if the owner requests map packs. No sample map may be labelled as a real ride map. An offline cold start with no prior verified account/ride must fail safely rather than invent access.

## Dependencies and ownership decisions

The Day 26 infrastructure choice is on the critical path. A publicly reachable HTTPS API and private database are required for a laptop-independent **online** ride. The service host, domain/TLS, routing capacity, durable media store and operating budget must be selected before building the Day 30 candidate. Firebase/FCM credentials must be verified if Android background push is part of that candidate. The app may use Supabase Auth, but its publishable key alone does not host Ridr's domain API or ride data.

If infrastructure or offline cold-start work is not ready, an APK can still be installed and open, but it must be described as a **limited offline preview**, not a complete standalone beta. The Day 30 gate is not satisfied by an Expo development client, a JS export, a localhost/LAN endpoint, or a passing simulator test.
