# Days 26–35: standalone Android candidate, offline recovery and release evidence

This plan supersedes Days 26–35 in the original 35-day PDF. Days 1–25 and the Day 1 scope and release criteria remain unchanged. Work is incremental: finish and verify one day's gate before implementing the next. A date never turns a failed gate into a pass.

## Constraints and release decision

The owner wants an Android APK that installs and runs without a laptop, costs nothing to host, needs no payment card, and supports offline use. The owner also requires production reliability. No evaluated no-card free stack provides a verified production availability commitment for Ridr's live sharing and SOS path. **The free-stack track below is a capped beta candidate, not production approval.** Production release remains blocked until hosting, recovery, and end-to-end safety delivery meet the Day 1 criteria. Do not use a keep-alive request, account cap, or passing unit test as evidence of guaranteed availability.

Voroa is a **candidate** host for a small Node API, not an approved deployment. Its free service currently stays running but has 512 MB RAM, 0.1 shared vCPU, no persistent filesystem, no horizontal scaling, and no support response commitment. Its managed database does not currently provide self-service PostGIS. The proposed split is Voroa for a measured lightweight API, the existing Supabase project for Auth and potentially PostGIS, and a separately verified routing source. Provisioning and compatibility must be tested before any endpoint enters an APK. Supabase Free can pause for low activity. If the API, database, routing, or quota check fails, stop the deployment path and record the blocker; do not silently switch providers or weaken a safety gate.

The current NestJS API, Socket.IO transport, private PostgreSQL/PostGIS schema, two Pune OSRM services, private media and status viewer cannot simply be copied into one free container. Moving ride data into hosted Supabase requires a reviewed migration of privileged roles, access rules, schema and tests. Moving to Cloudflare Workers or Supabase Edge Functions would require a separate API/runtime design, and neither can host the existing OSRM processes unchanged. Keep credentials out of Git and the APK.

## Standalone and offline acceptance

The Android candidate must be a signed internal/release-style APK with bundled JavaScript and native code, stable application ID and increasing version code, no development launcher or Metro dependency, and no cleartext, LAN or localhost endpoint. Prove clean install and upgrade on a physical phone. With the Mac off and USB disconnected, test over ordinary mobile data: sign-in with a verified account, ride read and two-member exchange, online road map, and a reachable hosted API. Save the APK, SHA-256 checksum, backend version, configuration without secrets, install instructions and device evidence. An Expo export or development-client APK does not pass.

Offline support remains the Day 1 bounded continuation of a **previously opened, authorized ride**. Cache an encrypted, account-scoped last-known ride summary and route information with expiry and explicit stale status. Preserve eligible location capture only while consent and OS permission remain valid. Keep encrypted location, text and preset queues across restart, show pending capacity, and record local stop-sharing/end intent without claiming server acceptance. On reconnect, fetch authoritative ride/session state first; deduplicate IDs, respect consent epochs and remote end, then replay safely. Run the Day 1 ten-minute outage with app restart: fresh live position within ten seconds and queued history/text within sixty seconds after stable reconnect.

Offline SOS must visibly say **“Not sent — offline”** and must not imply that contacts or emergency services were reached. If an online SOS is not acknowledged, show that uncertainty and offer a direct phone call or system share action initiated by the rider. Push-provider acceptance is not device receipt. New sign-in, create/join, route calculation or save, media upload, live peer positions, remote alerts, external status links and third-party road tiles still need connectivity. Downloadable offline map packs remain outside the Day 1 baseline; show an unavailable map rather than a sample map presented as a real ride. An offline cold start without a previously verified account/ride must fail safely.

## Capacity and failure rules

- Decide admission by **simultaneous active rides and measured request/bandwidth rates**, not total sign-ups. Batch eligible location updates without violating the Day 1 freshness target; cache route results; avoid proxying map tiles through the API. Set a cap only after Day 32 testing.
- On a service outage, preserve local ride data and pending actions, show stale/unsent state, and retry safely after authoritative reconciliation. The phone cannot deliver live sharing or remote SOS alerts while the service or network is unavailable.
- Monitor API errors/latency, database use, quotas and push receipts. Test restoration rather than treating backup existence as recovery evidence. Free-tier pausing, quotas and lack of failover remain release risks even if the beta works during a test.
- The Day 1 50-member, five-second update, 99.5% uptime, safety-delivery, offline and device criteria are **not reduced** by this schedule. If cost/no-card and production reliability remain simultaneous requirements, the production gate stays open until a qualifying infrastructure arrangement is available.
