# Ridr Day 3 API and real-time contracts

This is the implementation contract for the beta, not a running API. It translates the [Day 1 decisions](../day-01/scope-and-decisions.md) and [Day 2 journeys](../day-02/journeys.md). The [event schema](events.schema.json) validates wire shapes; the [data model](data-model.md) defines persistence and transactional invariants. Day 4 will initialize executable services.

## Shared HTTP rules

- Base path `/v1`; JSON UTF-8; UUID identifiers; RFC 3339 UTC timestamps ending in `Z`; decimal degrees and metres; distances in metres, speed in km/h. Unknown measurements are `null`, never fabricated zeroes.
- Private requests use `Authorization: Bearer <Supabase access token>`. Verify signature, issuer, audience, expiry, verified email, and application account/session status on every HTTP request and socket command. Derive the actor from that token; reject client-supplied `actorId`, `userId` or roles outside explicitly named target fields. Supabase Auth owns passwords and recovery; clients never receive a service-role key.
- PostgreSQL/Storage access goes through the backend. Database grants and storage policies deny direct client access to private tables/objects. A valid JWT alone is not authorization to read a particular ride.
- Validate required fields, lengths, enums and coordinates; reject unknown request properties. Strings are plain text, not executable HTML. Resource IDs, upload IDs, sequence cursors and invitation previews do not grant access. Use a non-enumerating `404` for another account's private resource.
- Every mutation, including multipart requests, requires `Idempotency-Key: <UUID>`. Scope its receipt to `(actor,key)`; include method, canonical path and body in the request digest, and save that digest plus result in the same transaction as the mutation. A same-key/same-digest retry returns the existing result; a different method, path or body returns `409 IDEMPOTENCY_CONFLICT`. Retain receipts for at least the 24-hour retry window; event IDs have a unique ledger through the ride's retention/deletion horizon.
- Concurrent resource edits require `If-Match: "<revision>"`; absence returns `428 PRECONDITION_REQUIRED`, mismatch `412 REVISION_CONFLICT`. Action-specific exceptions below use atomic uniqueness/guards instead. A revision increases only on accepted change. Idempotent replay is checked before revision conflict so an accepted retry succeeds.
- Success returns `{data: <resource>, requestId: UUID}`. Mutation failure is not a successful receipt; retryable transport/service failures do not consume an accepted result. Secret creation is a documented exception: persist only a token hash/redacted result, return the raw invitation/QR/status token once, then return metadata with `tokenAvailable:false` on retry; revoke/reissue explicitly if necessary. Creation is `201`, accepted background work `202`, reads/updates `200`, deletion with no representation `204`. Collection data is `{items: [...], nextCursor: string|null}`; `limit` defaults to 50 and is at most 100. Opaque cursors bind the resource, ordering and requesting actor; stable ordering uses server sequence or `(createdAt,id)`.
- Error body is `{error:{code,message,requestId,fields?}}`; `fields` is a map of request field names to plain-text validation messages. Never return credentials, raw SQL, contact values, bearer tokens or another member's private state in errors.
- `400 INVALID_REQUEST`, `401 UNAUTHENTICATED`, `403 FORBIDDEN`, `404 NOT_FOUND`, `409 STATE_CONFLICT`, `410 EXPIRED`, `413 PAYLOAD_TOO_LARGE`, `415 UNSUPPORTED_MEDIA_TYPE`, `422 VALIDATION_FAILED`, `429 RATE_LIMITED` with `Retry-After`, and `503 TEMPORARILY_UNAVAILABLE` are shared errors. More specific codes below retain these HTTP classes.
- Apply account/IP throttles to auth/invite lookup, per-member quotas to writes and storage, and separate reserved capacity for manual SOS. Do not require an advertisement, optional permission or entitlement for core coordination. Numeric abuse limits are deployment configuration to be verified before beta release.

## Common resources and validation context

| Resource | Required fields and meaning |
|---|---|
| `Profile` | `id`, `displayName` (1–80 characters), `createdAt`, `revision`; `id` is the authenticated Supabase user ID. Read `/me` also returns `activeMembership`, `entitlement: {adFree:boolean, evaluatedAt}` and deletion state. An unavailable entitlement check means no ad request/render. |
| `Ride` | `id`, `name` (1–80), `transport` (`motorcycle`, `cycling` or `car`), `state` (`lobby`, `active`, `ended`), `leaderMemberId`, `createdAt`, `startedAt:null\|timestamp`, `endedAt:null\|timestamp`, `revision`, `settings:{broadcastIntervalSeconds:5\|10\|15,stragglerDistanceM:200..2000}`. Default interval 5, straggler distance 500. |
| `Membership` | `id`, `rideId`, `profileId`, `displayName`, derived `role`, `physicalRole:rider\|pillion`, `joinedAt`, `leftAt:null\|timestamp`, `sharingEnabled`, `consentEpoch`, `revision`. `role=leader` exactly when this member is `Ride.leaderMemberId`; authority is not stored twice. Sharing is initially off. No member exposes private contacts. |
| `Position` | `{lat:-90..90,lon:-180..180,accuracyM:0..100000,recordedAt:timestamp}`; finite numbers only. `speedKph:null\|0..500`, `headingDegrees:null\|[0,360)` are separate fields where relevant. A location's age uses `recordedAt`, not reconnect time. Samples of accuracy >50 m or age >30 seconds remain labelled degraded/stale and are excluded from proximity/order calculations. |
| `Motion` | `{state:stopped\|moving\|unknown,observedAt:timestamp,source:speed\|activity\|unavailable}`. Stationary-only writes require `state=stopped`, a non-unavailable source and an observation no more than 30 seconds old at capture. Hysteresis is >6 km/h for 5 seconds to enter moving, <3 km/h for 10 seconds to exit. Available own telemetry must not contradict the observation. Unknown/stale active-ride motion is restricted. |
| `Pair` | `id`, `rideId`, `riderMemberId`, `pillionMemberId`, `status:active\|ended`, `formedAt`, `endedAt`, `revision`. Only one active pair per person; motorcycle transport; both current members consent. Leader is physically a rider. |
| `Message` | `id` (client event ID), `rideId`, server-derived `authorMemberId`, `kind:text\|preset\|pin\|voice`, `capturedAt`, `acceptedAt`, `sequence`, typed payload from the schema. Text ≤1,000 characters; pin label ≤1,000; voice ≤30 seconds, using an accepted private media ID. |
| `Sos` | `id` (original request ID), `rideId`, `reporterMemberId`, `kind:manual\|possible_crash`, `capturedAt`, `acceptedAt`, `sequence`, `position:null\|Position`, server-derived `pairSnapshot:null\|{pairId,riderMemberId,pillionMemberId}`, `linkedSosIds`, append-only `resolutions`, and per-device receipt metadata. Acceptance does not mean delivery to everyone. |
| `Summary` | `rideId`, own `memberId`, `recordedDistanceM`, `participationDurationSeconds`, `elapsedPaceMinPerKm:null\|number`, own recorded trail and quality gaps, explicit sharing-stop/leave points, shared route/photos, `updatedAt`, `expiresAt`. Pace = duration minutes / recorded kilometres, including stops; zero distance is `null`. Planned route never substitutes for recorded distance. |

`Motion` is validation context, not a persistent location stream or proof of actual safe riding. Clients use available permitted sensors; denying/turning off tracking never silently enables GPS. If there is no fresh usable motion source during an active ride, composition remains restricted but presets, SOS and stopping sharing remain available. Outside an active ride, unknown movement does not block onboarding/permission recovery. Paired accounts do not inherit each other's movement permission.

A stationary action includes `motion` and `capturedAt` in its body. The schema enforces the stopped shape; the service checks freshness and relevant telemetry. Offline composition may replay only with its original contemporaneous context and timestamps, while the same ride is active; a caller cannot relabel an old moving observation as newly stopped. This is a best-effort guard on client-reported signals, not device attestation.

## Ride and membership operations

Write authorization is evaluated again inside the committing transaction. A preview or earlier snapshot is never a reservation.

Day 6 implements creation, invitation preview/join, the current-member snapshot,
the caller's ride collection, and Lobby invitation replacement/revocation. Its
snapshot is `{ride,membership,members}`; the fuller snapshot in the table remains
the target for later location, pairing and real-time milestones. Creation also
returns `invite: {id,code?,url?,expiresAt,tokenAvailable}`. Preview returns the
opaque `rideId` needed for explicit join, without granting membership. These
additions clarify the original Day 3 response omissions.

`GET /rides?limit=&cursor=` returns only the caller's current Lobby/Active
memberships as `{items:[{ride,membership}],nextCursor}`. Lobby invitation replacement
accepts `{rotate:true}` and requires the ride revision; it returns the same
invitation shape as creation. Day 7 adds Active replacement with the stationary
motion context shown below. Raw invitation credentials are omitted on receipt replay;
receiving a link, QR or preview never joins a ride or enables location sharing.

Day 7 adds the lifecycle and proposal operations below, plus
`GET /rides/{rideId}/management` returning `{ride,membership,proposals}`. It returns
only the caller's latest membership and pending proposals involving that member.
Each proposal is `{id,kind,requesterMemberId,targetMemberId,physicalRole,expiresAt}`;
`kind` is `role_change` or `leadership`, with `physicalRole:null` for leadership.
Former participants may read this minimal response to reconcile an end/leave,
with no proposals or other members' data; outsiders cannot. The live snapshot
still requires current membership in a Lobby/Active ride.

Day 7 implements only the stop (`enabled:false`) branch of sharing. Explicit
opt-in, location delivery and durable offline command queues remain later work.
The app refreshes management while its ride screen is in the foreground; Day 7
records transactional events but does not yet deliver live ride socket events.

|---|---|---|

| `POST /invites/preview` | `{code}` or `{token}` → `{rideName,transport,state,availableRoles,expiresAt}` | Verified account; rate limited; no member names/locations/chat or automatic join/tracking. Exactly one input. Uniform `404 INVITE_UNAVAILABLE` for invalid/revoked/expired/ended; possession grants preview only. |
| `POST /rides/{rideId}/join` | `{inviteCode?:string,inviteToken?:string,physicalRole:rider\|pillion}` → `{ride,membership}` | Exactly one invitation credential; verify inside atomic join. Limit 50 current people including pillions, `409 RIDE_FULL`; joining an Active ride must claim the person's active-ride guard (`409 ACTIVE_RIDE_CONFLICT`); Lobby join does not claim it; no leader self-assignment. Same accepted retry returns same membership. Pillion only for motorcycle ride. No `If-Match`. |
| `GET /rides/{rideId}` | No body → `{ride,members,pairs,route,latestLocations,ownSharing,openSos,sequence}` | Current member for lobby/active snapshot. Includes own readiness/pair detail; leader receives full readiness/headcount. Others do not receive full private readiness records. Departed member uses historical routes only. Snapshot is consistent through its returned sequence. |
| `PATCH /rides/{rideId}/settings` | `{stragglerDistanceM?,broadcastIntervalSeconds?,motion,capturedAt}` → `Ride` | Current leader, stationary; lobby/active; `If-Match`. At least one setting; validate bounds. Threshold change invalidates obsolete warning timers. |
| `POST /rides/{rideId}/invites` | `{rotate:true,motion,capturedAt}` → `201 {code,url,expiresAt}` | Stationary leader; `If-Match` ride revision; revoke preceding invite atomically. Valid until earliest 24 hours, rotation or end. Code/token are secrets: never in logs, analytics or private snapshot. |
| `DELETE /rides/{rideId}/invites/current` | No body → `204` | Leader; immediate idempotent revocation; no motion gate for revocation. |
| `POST /rides/{rideId}/start` | `{motion,capturedAt}` → `Ride` | Stationary leader; Lobby only; `If-Match`. Lock ride/members/pairs, claim every participant's active-ride guard (reject `409 ACTIVE_RIDE_CONFLICT` atomically), and reject outstanding readiness with `409 PAIR_NOT_READY` plus authorized affected pair IDs. Atomically Active; clients still need each person's sharing consent and OS permission. Repeating accepted start returns original start. |
| `POST /rides/{rideId}/end` | `{reason:completed\|cancelled,capturedAt,consentEpoch}` → `Ride` | Current leader, including moving/unknown; Lobby cancellation or Active completion; no revision precondition, idempotent already-ended result. End time is server authority. Stop local tracking immediately even while offline; only acceptance makes global end certain. |
| `POST /rides/{rideId}/leave` | `{stoppedAt,consentEpoch}` → `{leftAt,revision}` | Own current membership; no motion or revision gate for privacy exit. Leader gets `409 LEADER_MUST_TRANSFER_OR_END`, but can always stop own sharing. Revoke live access/links, close the consent interval at original local `stoppedAt`, and clear pair/readiness/active guard atomically. |
| `POST /rides/{rideId}/role-proposals` | `{targetMemberId,physicalRole:rider\|pillion,motion,capturedAt}` → `201 {proposalId,expiresAt}` | Leader, stationary; `If-Match` ride. Target must still be current; no implicit acceptance. Proposal expires in 5 minutes or on state/membership revision change. |
| `POST /rides/{rideId}/role-proposals/{proposalId}/accept` | `{motion,capturedAt}` → `Membership` | Named target only; stationary; current proposal; server serializes with pair/ride change. Clear affected pairing/readiness. Current leader cannot become pillion without prior transfer. |
| `DELETE /rides/{rideId}/role-proposals/{proposalId}` | No body → `204` | Proposer or target; decline/cancel idempotently. |
| `POST /rides/{rideId}/leadership-proposals` | `{targetMemberId,motion,capturedAt}` → `201 {proposalId,expiresAt}` | Leader; target already physically Rider and current; 5-minute proposal tied to ride revision. Pillion must first accept Rider role change. |
| `POST /rides/{rideId}/leadership-proposals/{proposalId}/accept` | `{motion,capturedAt}` → `Ride` | Named Rider target only; stationary. Lock both memberships and ride; change `leaderMemberId` once. Previous leader becomes derived Rider; valid motorcycle pairing survives. Stale/crossed proposals `409 PROPOSAL_STALE`. |
| `DELETE /rides/{rideId}/leadership-proposals/{proposalId}` | No body → `204` | Proposer or target. Disconnect is neither acceptance, leave nor automatic transfer. |
| `PUT /rides/{rideId}/sharing` | `{enabled:true}` or `{enabled:false,stoppedAt,consentEpoch}` → `{enabled,consentEpoch,revision,effectiveAt}` | Own current membership only. Enable requires Active, explicit opt-in and available permission; never on deep-link open/join. Stop is always permitted, including moving/unknown; increment consent epoch and revoke external links atomically. Stop records original local `stoppedAt` as capture cutoff (separate from server revocation time); validate it against the epoch interval and cap it at receipt time. Stop needs no revision precondition. Enable requires `If-Match` with the last acknowledged sharing revision; service serializes consent changes, and deduplicated stale stop retries cannot cancel a newer explicit enable. |

All active-access revocation operations evict the corresponding sockets/subscriptions as part of post-commit delivery. Transaction checks remain authoritative if eviction delivery is delayed. Leaving retains historical access only to participated completed data within retention; stop sharing retains live membership, role, pairing, map/chat/presets and SOS.

| Method/path | Request → response | Authorization, concurrency and failure rules |
|---|---|---|
| `GET /rides/{rideId}/route` | No body → `{id,source:gpx\|drawn,profile:cycling\|driving,points:[{lat,lon}],revision}` or `null` | Current member; completed participant via history. No route yields unavailable ordering, never a guessed path. |
| `PUT /rides/{rideId}/route` | `{points,motion,capturedAt}` → saved route | Stationary leader; Lobby only; `If-Match` route (or `If-None-Match:*`). Route algorithm/profile failures preserve existing route. |
| `POST /rides/{rideId}/route/import` | Multipart `file` GPX ≤5 MB, JSON-string `motion`, `capturedAt` → saved route | Same guard; XML external entities and DTD disabled; only GPX, ≤10,000 points. `413`, `415`, or `422 INVALID_ROUTE` leaves earlier route intact. Import does not silently upload arbitrary files to shared media. |
| `POST /rides/{rideId}/pair-invitations` | `{motion,capturedAt}` → `201 {pairInvitationId,token,expiresAt}` | Unpaired current motorcycle Rider/Leader or Pillion; issuer's named consent is recorded. | `POST /rides/{rideId}/pair-invitations/preview` | `{token,motion,capturedAt}` → `{pairInvitationId,counterpart:{memberId,displayName,physicalRole},expiresAt}` | Current stationary member; same ride, opposite physical role, neither already paired; scanning only previews. | `POST /rides/{rideId}/pairs` | `{pairInvitationId,token,consent:true,motion,capturedAt}` → `201 {pair,readinessScanReceiptId}` | Scanning counterpart's explicit consent, issuer consent still current; atomically consume token and create both pair guards. | `DELETE /rides/{rideId}/pairs/{pairId}` | `{motion,capturedAt}` → `204` | Either pair member, stationary, no counterpart approval. End pair/reset readiness/individual markers atomically. Leave/end/account deletion also clear pairs without a separate scan. |
| `PUT /rides/{rideId}/pairs/{pairId}/readiness/me` | `{helmetConfirmed:boolean,ready:boolean,scanReceiptId,motion,capturedAt}` → `{pairId,memberId,helmetConfirmed,ready,confirmedAt}` | Current pair's Pillion only, own attestation and current scan receipt. Readiness requires true values and current pair revision. Leader cannot attest as pillion. Use own membership/pair expected revision; pending offline is not confirmed. |
| `POST /rides/{rideId}/pairs/{pairId}/scan-challenges` | `{roundId:null\|UUID,motion,capturedAt}` → `201 {challengeId,token,expiresAt}` | Stationary current pair member; bind QR to this pair revision and current headcount round (or null for readiness), single use, 5-minute expiry. Secret returned once; explicit reissue revokes previous unconsumed challenge. |
| `POST /rides/{rideId}/pairs/{pairId}/scan-receipts` | `{challengeId,scannedToken,motion,capturedAt}` → `{scanReceiptId,pairId,expiresAt}` | Current pair member or leader doing the current rest-stop scan; fresh single-use scan challenge, 5-minute expiry, same ride/pair. Does not itself set anyone else's helmet/readiness attestation. |
| `POST /rides/{rideId}/headcounts` | `{motion,capturedAt}` → `201 {id,state:open,pairIds,confirmedPairIds:[],revision}` | Stationary leader, Active; one open round; snapshot current pairs. Previous round's checks do not carry forward. |
| `PUT /rides/{rideId}/headcounts/{roundId}/pairs/{pairId}` | `{scanReceiptId,motion,capturedAt}` → headcount progress | Stationary leader scans current pair using this round's fresh receipt; the current round needs a fresh leader scan, without repeating the pillion's pre-start helmet attestation. Duplicate scan counts once. Changed pair invalidates its old confirmation and updates required set. |
| `POST /rides/{rideId}/headcounts/{roundId}/complete` | `{motion,capturedAt}` → completed headcount | Stationary leader; `If-Match` round. Lock round/current pairs and require every current pair's fresh confirmation. `409 HEADCOUNT_INCOMPLETE` otherwise. Offline local results cannot complete the server round. |

A pairing QR establishes both identities and consent; a rest-stop scan is a new challenge tied to pair revision and round. These must not share a reusable consumed token. The scan-receipt path consumes its separate `challengeId` plus `scannedToken`; only a pair member can issue the QR, and only an authorized counterpart or leader can consume it for the stated purpose. The accepted pairing transaction records the consumed initial scan as a challenge/receipt tied to the newly formed pair and returns `readinessScanReceiptId`; the pillion can use that pair-bound receipt for their own attestation. Rescanning after expiry uses a new challenge. Rest-stop rounds require a fresh leader scan of each current pair; they do not require a new helmet attestation from each person. Scans are human confirmations, not helmet-safety verification.

## Messages, media and history

Day 14's implemented voice path uses `POST /rides/{rideId}/media/voice` with one `audio/mp4` AAC file (maximum 5 MB), `mediaId`, `capturedAt`, and JSON `motion` form fields; `Idempotency-Key` equals `mediaId`. The API validates the actual container, codec and duration (maximum 30 seconds), then commits the ready media row and ordered voice message together. `GET /rides/{rideId}/media/{mediaId}/content` rechecks active membership and serves private bytes with `Cache-Control: private, no-store`. The generic signed-upload/photo flow below remains a later design contract, not a deployed Day 14 endpoint.

## SOS, receipts and reconnection

- `sos.request` is allowed to every current active member irrespective of motion, location consent, map/push availability or crash-detector setting. `possible_crash` records an explicit user SOS action from the conditional prompt; there is no automatic non-response escalation endpoint.
- On one tap, create a durable local UUID event and immediately attempt delivery. Snapshot the available permitted location or `null`; never acquire GPS implicitly after sharing stopped. Server derives the pair at the validated original capture time from historical pair/membership intervals, never from a client-supplied pair identity. Preserve that snapshot after later unpairing; uncertain timing is labelled rather than assigned to a new counterpart. Link simultaneous requests involving that pair without suppressing either reporter/event ID.
- `GET /rides/{rideId}/sos/{eventId}` returns `{status:accepted,sos}` or authenticated `404 SOS_NOT_ACCEPTED`. The latter is definitive only after current session/member state is reconciled. A network error is uncertainty, not proof of non-acceptance. Accepted status is queryable by a still-authorized participant after end until retention/deletion.
- Retry unaccepted SOS with its same ID for up to 60 seconds from original capture. On reconnect first query that ID; an accepted result always wins over a pending local retry. After 60 seconds, require an explicit reconfirmation before any fresh send. Do not mutate an accepted original request.
- `POST /rides/{rideId}/sos/{eventId}/reconfirm` with `{event:<original sos.request>,confirmedAt}` and a fresh mutation key first locks the original ID's ledger and queries acceptance. If accepted, return the original `Sos`. If absent and ride still Active, reserve the same event ID with a short server reconfirmation grant `{grantId,eventId,expiresAt}` (30 seconds), then allow the same request ID/payload with that grant in transport metadata. Validation accepts fresh help intent without changing original capture/position age. Grant is bound to actor/ride/original digest, one-use, never a bypass after end. An expired/unknown grant returns `409 RECONFIRMATION_REQUIRED`. Persist the grant as metadata in that reconfirmation command receipt, with its command ID as `grantId`, original event ID/digest, expiry and consumed state. Reconfirmation and SOS acceptance serialize on the same transaction advisory lock for `(actor,eventId)`; issuing a grant is not an accepted SOS or recipient notification.
- `sos.resolve` appends `{sosId,resolution:reporter_okay|coordination_closed,reason?}`. Only the original reporter can report okay; only the current leader can close coordination, with a nonempty reason. Each resolution has its own UUID. Neither erases the original SOS, and leader closure never claims the reporter is safe. Offline okay remains pending until accepted.
- `POST /rides/{rideId}/sos/{eventId}/receipts` with `{deviceId,receivedAt}` records receipt by this authenticated device/member only. Idempotent device/event key; server timestamps receipt separately. A device receipt is not evidence the human read it. Push delivery is a hint to fetch, never an authoritative change of SOS state.
- Connection loss has distinct local states: `not_sent_offline` if never transmitted; `delivery_unconfirmed` after transmission without acknowledgement; `accepted` only after an accepted response/reconciliation; `reconfirmation_required` after the freshness limit and status query. No contract promises emergency services or automatic contact messaging.

## Owner-only external status links

| Method/path | Request → response | Authorization and expiry |
|---|---|---|
| `POST /rides/{rideId}/status-links` | `{lifetimeHours?:1\|4\|8\|24}` → `201 {linkId,url,tokenAvailable:true,expiresAt}` | Owner must be current Active member with sharing enabled. Default 4 hours; no target-person field. Server generates 256 random bits; database stores SHA-256 hash only. URL token is returned once. Same-key retry returns original metadata with `url:null,tokenAvailable:false`; explicitly revoke/recreate with a new key if original response was lost. |
| `GET /rides/{rideId}/status-links` | No body → own `{linkId,createdAt,expiresAt,revokedAt}` collection | Owner only; never recover raw token or list another person's links. |
| `DELETE /rides/{rideId}/status-links/{linkId}` | No body → `204` | Owner; idempotent and motion-independent; immediate server authorization revocation. Offline display remains pending until acknowledgement. |
| `GET /public/status` | `Authorization: Bearer <link token>` → `PublicStatus` | No account required; token hash lookup and current owner/ride/sharing/revocation/absolute-expiry check on every read. Invalid/revoked/expired all return `410 STATUS_UNAVAILABLE` with no status fields. No user writes or private socket subscription. |

`PublicStatus` is exactly `{displayName,rideState,lastPosition:null|Position,sosState:none|open|reporter_okay|coordination_closed,servedAt,leaseExpiresAt,linkExpiresAt}`. Do not include membership/ride IDs, pairing identities, group markers, chat, contacts, history, route or photos. `lastPosition` is only the owner's independently recorded position, even when their group marker uses their rider's location. Labels retain timestamp/accuracy; no claim of live freshness for stale data.

Links use a browser fragment, for example `https://<viewer-origin>/status#<token>`; the viewer immediately removes it from visible history, retains it only in memory, and sends it through the Authorization header. Set `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, a restrictive CSP and no third-party analytics/scripts. Do not put credentials in query strings, traces, error capture or access logs; redact Authorization headers for both private and public requests.

The public response is validated against `#/$defs/PublicStatus` in the event schema, not against the root event union. On successful public reads `rideState` is `active`; ended rides return `410` immediately. Every successful read grants at most a 15-second display lease, capped by absolute link expiry; renew every 5 seconds. Start a conservative monotonic deadline at request dispatch, adding at most `leaseExpiresAt - servedAt` (never from response arrival), clearing on expiry, rejection or a visibility resume before revalidation. HTTP/browser/service-worker caches cannot extend it. Do not interpret stale network failure as permission to keep the last display. A screenshot of previously received data cannot be revoked; the UI promises bounded live display, not erasure from a recipient's memory.

Server end, owner leave, sharing stop, deletion or explicit revoke invalidates reads immediately. Queued privacy changes reconcile before location replay; the interface discloses that offline revocation can only be enforced on server receipt, with the original expiry as upper bound.

## Socket transport, event ledger and replay

1. Connect Socket.IO namespace `/v1/rides` over TLS with a verified access token in the authentication payload, never query params. Send `{rideId,afterSequence}` to subscribe. Authorize current membership on connect, subscribe and every write; eject on session/member revocation and token expiry. External viewers cannot join this namespace.
2. The event-schema root is a strict `oneOf` of client commands, `server.ack`, and `server.event`. `v:1` is mandatory; unknown version/type/property returns a validation error. Schema format checks (UUID/UTC) must be enabled, not treated as annotations. Client identity always comes from transport auth.
3. Accept `command` with `{event:<client envelope>,reconfirmationGrantId?:UUID}`. HTTP fallback uses the event as its body and optional `X-SOS-Reconfirmation-Grant` header. The grant is transport metadata and does not alter the immutable event digest. ACK is sent only after authorization, validation and database commit. A retry gets the same accepted event ID and sequence.
4. For each accepted command, atomically write its domain record, unique `(actor,eventId)` receipt, monotonic per-ride server sequence and outbox notification. The ID ledger also binds ride/type/payload digest. For `location.sample`, `capturedAt` must equal `payload.position.recordedAt`. Same ID with another body gets `IDEMPOTENCY_CONFLICT`, not another message. Outbox workers retry safely; subscribers deduplicate server event IDs/sequence. Delivery is at least once, not exactly once.
5. `server.event` carries typed location/message/SOS updates or a resource invalidation with the new revision. Invalidation tells authorized clients to refetch the role-filtered snapshot; never broadcast private contacts/readiness as a generic full-row change. Straggler/battery warning types are separate from SOS and have an expiry. Server time, event ID and sequence are authoritative; client capture time describes the original observation.
6. Reconnect order: refresh auth → fetch snapshot/current state → apply queued stop-sharing/leave/end/revoke/deletion actions → reconcile uncertain accepted IDs/SOS → obtain snapshot/cursor again → replay allowed current-session work → upload eligible historical samples separately. New opt-in is a separate explicit action after the last stop acknowledgement; old consent-epoch samples cannot become live after re-enable.
7. `GET /rides/{rideId}/events?afterSequence=&limit=` returns authorized replayable server events with `{items,nextSequence,hasMore}`. Do not replay expired warning/location payloads as current. For a missing/compacted cursor return `409 SNAPSHOT_REQUIRED`; refetch snapshot, then continue after its sequence. Acceptance receipts survive replay-log compaction within their retention window.
8. Latest live position advances only when `(recordedAt,eventId)` is greater than the stored ordering key and membership's consent epoch matches; older permitted samples go only to history. Reject capture times more than 5 seconds in server future (`CLOCK_SKEW`), preserve older timestamps, and never stamp a queued sample “now.” Samples older than 30 seconds cannot update a live marker or proximity decisions.
9. Location collection defaults to 5 seconds (5/10/15 options); freshness/accuracy gates, route-match confidence, paired-unit centroid counting and alert hysteresis remain Day 1 rules. Pillion observations retain their own trail but never move a combined rider marker. A server location event describes that member's sample, not an invented combined coordinate.
10. The encrypted client queue is bounded to 24 hours / 50 MB, with a visible capacity warning; prioritize manual SOS and privacy actions without silently dropping unacknowledged text. Immediate retry then exponential backoff/jitter capped at 30 seconds. Ended-ride queued text/presets are marked unsent with local-copy recovery. Stop/end prevents further local collection. Acknowledged prior samples can enrich history without restarting a session.

A rejected ACK is explicit and never assigned a successful sequence: `{v:1,type:"server.ack",id:<server UUID>,eventId:<client UUID>,status:"rejected",serverTime,code,retryable}`. An accepted ACK instead includes `rideId,sequence` and `status:"accepted"|"duplicate"`. Disconnect without an ACK remains uncertainty. Client validation errors do not become accepted events merely because they fit JSON Schema.

## Examples and implementation acceptance

A valid stationary text command (illustrative IDs/times):

```json
{"v":1,"type":"message.text","id":"10000000-0000-4000-8000-000000000001","rideId":"20000000-0000-4000-8000-000000000001","capturedAt":"2026-09-11T09:00:00Z","payload":{"text":"Regroup at the next stop.","motion":{"state":"stopped","observedAt":"2026-09-11T08:59:59Z","source":"speed"}}}
```

A manual SOS can use `payload:{"kind":"manual","position":null}` and the same envelope fields with type `sos.request`; it has no stationary or location-sharing prerequisite. Adding `actorId`, lat91, empty/1001-character text, negative accuracy, unknown event version, a text motion state of `moving`, or a preset outside the declared enum must fail schema validation. A structurally valid event can still fail service authorization, state, telemetry, consent-epoch or freshness checks.

Implementation acceptance must cover concurrent 50th joins/start/pair/transfer/end, account switching, participant versus external projections, contradictory/unknown motion, duplicate/lost ACKs, stale timestamps and consent epochs, accepted SOS reconfirmation races, current-round headcount, expired media/token leases, zero-distance summaries and deletion/retention. These are specified tests for later implementation; Day 3 checks only the design artifacts and machine-readable shapes. No endpoint is deployed by this document.
