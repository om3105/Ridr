# Day 23 — completed-ride photos

Participants can add a JPEG, PNG or WebP image to a point on a completed ride's planned route or their recorded, consented trail. The summary shows the author, point and image to eligible participants, with removal available only to its author. Upload requires a fresh stopped-motion check. The app keeps the chosen photo and its stable upload ID for a retry, and Cancel discards the local draft before upload.

The API decodes the actual file, rejects malformed or oversized images, rotates and recompresses it as a metadata-free JPEG, and caps the stored image at 2 MB. Content is served through authenticated participant checks with `Cache-Control: private, no-store`; files live outside the public app tree in `PHOTO_MEDIA_DIR` (by default `data/photos`). Access expires with the ride's 90-day history window. Removal first hides the database record, then removes the file. An hourly cleanup also removes expired media, media owned by deleting or deleted accounts, and old unreferenced files left by interrupted uploads. The media directory needs durable private storage in any deployed API environment.

Day 3 described a three-step signed-upload flow. This milestone uses one authenticated multipart endpoint because the existing API already has a private media path; the server still validates and processes the final bytes before publication. There are no public or signed photo URLs. The browser can view photos, while picking and uploading is available in the native app. Adding `expo-image-manipulator` requires a fresh native development or release build; a JavaScript update alone cannot add the module to an installed build.

## Verification

With the local test database running and migration 006 applied, run `NODE_ENV=test npm run test:photos --workspace @ridr/api`. It checks participant and outsider access, author-only removal, route validation, duplicate retries, pagination and deleted-account cleanup through the private file store and HTTP endpoints. Run `npm test --workspace @ridr/api`, `npm test --workspace @ridr/mobile`, `npm run typecheck`, `npm run lint` and `npm run build` for the broader project. For a phone acceptance check, install a new native build, sign in with two participant accounts, end a ride with a route or recorded trail, add a photo while stopped, verify it appears on both accounts, and check that the second account cannot remove it. Also try a nonparticipant account and remove the owner account to confirm access revocation and cleanup.

Phone UI behavior and durable-storage deployment remain release acceptance checks until exercised in those environments. The 90-day window is the current history policy; a future policy change must update both the photo and history rules together.
